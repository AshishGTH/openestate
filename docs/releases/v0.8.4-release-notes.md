# v0.8.4 release notes (DRAFT, not released)

Draft text, written with the database changes; the rest of the notes come with
the release.

### The API now listens on 127.0.0.1 only

Until v0.8.3 the API listened on every network interface, so anyone on your
network could reach `http://<server>:3000` directly and skip nginx (its TLS, its
limits, and the real client address used for rate limits and the audit log).
From v0.8.4 it listens on `127.0.0.1:3000`, and it believes forwarded headers
only from a proxy on the same machine. Nothing changes for an install that uses
the bundled nginx.

If something reached port 3000 directly, such as a monitoring check from another
machine or a reverse proxy or load balancer on a different host, it stops working
after the upgrade. Set `HOST=0.0.0.0` (or the address it should listen on) in
`/etc/openestate/openestate.env`, run `sudo systemctl restart openestate-api`,
and firewall port 3000 so only that proxy can reach it. A tunnel such as
`cloudflared` should point at nginx (port 80 or 443), not at port 3000.

### The upgrade script refuses to go backwards

From v0.8.4, `upgrade-native.sh` stops before backing up, building or changing
anything if the version you name is older than the one running, or if your
database already has changes that version does not contain. It says which, and
the current version keeps running. There is no option to force it: to go back
to an older version, restore the backup taken before your last upgrade with
`restore-native.sh`. It also checks that the code it builds is exactly the
commit it downloaded, and prints that commit ("Deploying <commit> (<version>)").
This protects upgrades run with the v0.8.4 script or later; the upgrade to
v0.8.4 itself still runs your current script, so give it the release tag.

### After the upgrade: check for links left unchecked

v0.8.4 puts back 71 database links (foreign keys) that a 2026-08 migration had
removed. Where existing rows already point at something that no longer exists,
the link is still added and checks every new or changed row, but it is left
"not valid" and nothing is changed or deleted. The upgrade never stops for this.
Because the upgrade to v0.8.4 runs your current (v0.8.3) script, which cannot
print that list, run this once afterwards:

```bash
sudo /opt/openestate-src/deploy/native/check-foreign-keys.sh
```

It only reads. It exits 0 and says so if every link is checked; otherwise it
lists each one with the table, column and number of rows involved, and exits 2.
From v0.8.4 on, the upgrade script prints the same list itself.

### If the upgrade stops at a migration

If the upgrade stops during the database migration, for example because it timed
out waiting for a busy table, nothing from that migration was applied and the
previous version keeps running. Before you run the upgrade again, mark the failed
migration as rolled back:

```bash
sudo -u postgres psql -d openestate -c "UPDATE _prisma_migrations SET rolled_back_at = now() WHERE finished_at IS NULL AND rolled_back_at IS NULL"
```

Without this, the next attempt stops with "P3009 ... found failed migrations".
The upgrade script in v0.8.4 and later prints this command itself; the v0.8.3
script, which runs this upgrade, does not.

The database is called `openestate` on every install made with
`install-native.sh`, and `upgrade-native.sh` only ever migrates a database of
that name. To check yours without printing the password in the same line, run:

```bash
sudo sed -nE 's#^DATABASE_URL=.*/([^/?"]+).*#\1#p' /etc/openestate/openestate.env
```

If your database runs on another server (you upgrade with `--db-host`), run the
command there, or add `-h <host> -U <superuser>` to `psql` instead of
`sudo -u postgres`.

v0.8.4 has several migrations, and they are applied one at a time. If the
foreign-key step fails, the earlier v0.8.4 migrations (the one that limits the
ledger escape hatch to the database superuser, and the one that moves the
portal-link check to its own owner) may already be applied. The previous version
keeps running correctly in that state: it never uses the escape hatch, and the
portal-link check behaves the same under its new owner.
