# Deploying the release candidate to staging

Branch: `chore/rc-with-deps` (release candidate + same-major dependency patches). Nothing here has been run on a staging
host; every check is **NOT TESTED** until you tick it.

## 0. What you need

- An Ubuntu 22.04/24.04 host with PostgreSQL, Redis, nginx, Node 20, git and a build toolchain (`make g++ python3`); the
  installer checks and tells you what is missing.
- A DNS name and a TLS certificate for it (for example `certbot certonly --nginx -d staging.example.com`).
- The API code and the database migration **deploy together**. Never apply the migration from a branch that is not the code you
  are deploying.

## 1. First install (empty host)

```bash
sudo git clone https://github.com/AshishGTH/openestate /opt/openestate-src
cd /opt/openestate-src && sudo git checkout chore/rc-with-deps
sudo ./deploy/native/install-native.sh --server-name staging.example.com
```

The installer generates every secret, writes `/etc/openestate/openestate.env`, creates the database roles, migrates, seeds and
starts `openestate-api`. The seeded admin password is printed once; store it in your password manager.

If the host already runs an OpenEstate install, upgrade instead:

```bash
cd /opt/openestate-src && sudo git fetch origin
sudo ./deploy/native/upgrade-native.sh --ref chore/rc-with-deps      # backup -> build -> migrate -> cut over -> health gate
```

**Upgrade stops silently after the backup ("would clobber existing tag")?** On a source checkout cloned **before the
history rewrite**, `upgrade-native.sh --ref ...` runs `git fetch --tags` inside `set -e`, git rejects the old tags
(`v0.1.0` to `v0.7.1`) with "would clobber existing tag", and the script exits without printing anything of its own, right
after the backup. Workaround (proven), then rerun the upgrade:

```bash
sudo git -C /opt/openestate-src fetch --tags --force origin
sudo ./deploy/native/upgrade-native.sh --ref chore/rc-with-deps
```

See also `docs/docs/installation.md` (upgrade section) and `docs/todo.md`.

The upgrade makes a backup first (`backup-native.sh`), applies the migration before switching releases, and rolls the code
back automatically if the health check fails. It never rolls the database back.

## 2. Environment variables (names only; values live in `/etc/openestate/openestate.env`, mode 640, never in git)

| Name | Set to |
|---|---|
| `NODE_ENV` | `production` |
| `PORT` | `3000` (nginx proxies to it; bind only on localhost) |
| `DATABASE_URL` | app role (row-level security enforced) |
| `DATABASE_URL_SYSTEM` | system role (BYPASSRLS) |
| `REDIS_URL` | the host's Redis |
| `CORS_ALLOWLIST` | the origins allowed to call the API from a browser (the native mobile app does not use CORS) |
| `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` | generated by the installer |
| `JWT_ACCESS_EXPIRES_IN` | `15m` (production value; needed for the expiry test) |
| `JWT_REFRESH_EXPIRES_IN` | `7d` |
| `PORTAL_JWT_REFRESH_EXPIRES_IN` | `24h` |
| `REFRESH_REUSE_GRACE_SECONDS` | `30` (default) |
| `DEFAULT_THROTTLE_LIMIT`, `PORTAL_AUTH_THROTTLE_LIMIT`, `TOTP_VERIFY_THROTTLE_LIMIT` | leave at the defaults; do **not** raise them for staging, that is how the real limits get tested |
| `PAN_ENCRYPTION_KEY`, `TOTP_ENCRYPTION_KEY`, `PLUGIN_SECRET_ENCRYPTION_KEYS` | generated by the installer |
| `UPLOADS_DIR` | a persistent directory writable by the service user |
| `SWAGGER_ENABLED` | `false` |
| `LOG_LEVEL` | `info` |

## 3. TLS front end

The installer's nginx site is plain HTTP. Replace it with the staging config in this folder:

```bash
sudo cp /opt/openestate-src/docs/staging/nginx.conf /etc/nginx/sites-available/openestate
sudo sed -i 's|__SERVER_NAME__|staging.example.com|g; s|__CERT_DIR__|/etc/letsencrypt/live/staging.example.com|g' \
     /etc/nginx/sites-available/openestate
sudo nginx -t && sudo systemctl reload nginx
```

`nginx.conf` passed `nginx -t` on nginx 1.24 in a sandbox after one fix (see `NGINX_LOCAL_CHECK.md`, including what that did
not cover: IPv6 and the static paths). Run `nginx -t` again on the staging host; it is the first check there.

**One proxy hop only.** The API trusts exactly one proxy in front of it (`trust proxy` = 1 in `apps/api/src/main.ts`), which is
this nginx. If a CDN, load balancer or tunnel is ever put **in front of nginx**, that setting must change with it. Otherwise
`req.ip` becomes the address of that extra hop and every client shares **one rate-limit bucket** (and the `Secure` cookie
decision, which follows `X-Forwarded-Proto`, can be wrong).

## 4. Health checks

```bash
curl -sS https://staging.example.com/api/v1/health           # {"status":"ok","db":"ok","redis":"ok","version":"..."}
curl -sSI http://staging.example.com/ | head -3               # 301 to https
curl -sSI https://staging.example.com/ | grep -i strict-transport
systemctl status openestate-api --no-pager | head -5
journalctl -u openestate-api -n 50 --no-pager                 # no error-level lines, no [audit] failures
```

Cookie check (the refresh design depends on it): log in with curl and confirm both cookies carry `Secure`:

```bash
curl -sSi -X POST https://staging.example.com/api/v1/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"<admin email>","password":"<password>"}' | grep -i '^set-cookie'
# expect: openestate_refresh=...; Path=/api/v1/auth; HttpOnly; Secure; SameSite=Strict   and   openestate_csrf=...; Secure
```

(Cookie names come from `apps/api/src/auth/auth.controller.ts` and `csrf-cookie-names.ts`.)

## 5. Migration check

Follow `MIGRATION_REHEARSAL.md`. Confirm the migration is recorded:

```bash
sudo -u postgres psql openestate -c "select migration_name, finished_at from _prisma_migrations order by finished_at desc limit 3;"
```

## 6. Checklist

| Check | Result |
|---|---|
| Install or upgrade finished with exit 0 | NOT TESTED |
| Health endpoint OK over HTTPS, version as expected | NOT TESTED |
| HTTP redirects to HTTPS; HSTS present | NOT TESTED |
| `nginx -t` passes with `nginx.conf` on the staging host | NOT TESTED (passed in a sandbox only) |
| Login returns `Secure` cookies | NOT TESTED |
| Migration `20260930120000_follow_up_type_is_site_visit` recorded as finished | NOT TESTED |
| No errors in the service journal after 10 minutes | NOT TESTED |
| Upload of a 10 MB file succeeds; 12 MB is refused with 413 | NOT TESTED |
| Mobile build pointed at `https://staging.example.com` (not the mock server) | NOT TESTED |

## 7. Rollback

Code: `upgrade-native.sh` does it automatically when the health gate fails. Database: forward-only; restore the pre-upgrade
backup (`restore-native.sh`) as a deliberate decision.
