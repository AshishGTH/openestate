# v0.8.2 — security release: plan only

**Status: plan for approval. Nothing described here has been built.** This
document is intentionally not committed. Split from the original
combined plan: this file covers the security fixes (Parts C, D, F),
shipped first, with its own advisory. The database-integrity work
(the 71 foreign keys, the manifest, the CI guards) is now
`docs/testing/v0.8.3-plan.md`, shipped second.

## For the owner, in plain words

This release closes two real gaps, found while investigating a smaller
one:

1. **A staff-login check that looked at the wrong field**, which is how
   two old test accounts of yours were able to reach staff sign-in at
   all — narrowly, reaching only already-public actions, nothing
   belonging to another customer or the business.
2. **A bigger one, found while answering a follow-up question: today,
   any admin who can create or edit a staff user can hand them the
   `super_admin` role, or reset that user's password and see the reset
   link on screen — even if the admin doing it holds far fewer
   permissions than the account they're touching.** This is a real
   account-takeover path using nothing but the ordinary "Add User" /
   "Edit User" screens. It's the headline fix in this release.

On the two old accounts: real evidence from your own server's release
history places what was running around the time they were most likely
created well before a fix (shipped 2026-09-24) that closed a separate
bug where some writes didn't leave an audit trail. So the honest record
is: **created through the app itself, at a time when the app didn't yet
check what we now check — not created by some outside script**, unless
further evidence says otherwise. This replaces an earlier, wrong guess
in this investigation that they were created outside the app entirely.

## Answers to the architect's five questions (read-only investigation, before any revision)

**Q1 — can a caller holding `ADMIN_USER_UPDATE` (e.g. `company_admin`)
act on a user whose role holds permissions the caller lacks (e.g. the
`super_admin` seeded admin)?**

| Action | Yes/No | Code path |
|---|---|---|
| `forcePasswordReset` | **YES — and this is a full account takeover, confirmed.** | `UsersService.forcePasswordReset()` checks only that the target isn't deactivated and isn't a portal account. No check against the target's role or permissions. The function **returns the raw reset token to the caller** — so a `company_admin` calling this against the seeded `super_admin` account gets a live, usable reset link for it on screen. |
| `resetTotp` | **YES.** | Same shape — checks only "not self, not portal." No role/permission comparison. Clears the target's 2FA, no password needed. Combined with the row above: reset password + clear 2FA = complete login as `super_admin`, no other credential needed. |
| `deactivate` / `reactivate` | **YES.** | `UsersService.deactivate()`/`reactivate()` check only that the target exists in the caller's company. No role/permission check at all — a `company_admin` can deactivate the real `super_admin` account outright. |
| `update` (role, email, phone) | **YES.** | `UsersService.update()` only validates the *new* role's portal/staff shape (`assertRoleFitsAccount`) — nothing compares the target's *current* role's permissions against the caller's own. A `company_admin` can silently change the `super_admin` account's email or phone (breaking their recovery path) or reassign their role entirely. |

**Can a user change their own role?** **Yes.** `update()` places no
restriction on the target id being the caller's own — a `company_admin`
can `PATCH /users/<their own id>` with `roleId` = the `super_admin`
role's id and self-promote directly. No second account, no other
credential needed. This is the single most direct escalation found in
this investigation.

**Can a `company_admin` edit the `super_admin` role's permission set,
or its own role's?** **Yes, to both.** `RolesService.update()` checks
only (a) a system role can't be renamed, and (b) a portal role can only
hold portal permissions. **Nothing checks that the editor's own
permission set already contains what they're about to grant.** A
`company_admin` can `PATCH` their own role and add every remaining
permission (all `portal.*` keys — everything `company_admin` doesn't
already have) directly, with no user account involved at all. This is
even more direct than the user-role path above.

**Q2 — does refresh rotation re-check the user (`isActive`, portal/staff
consistency)? Can a deactivated user keep refreshing?**

**Partially — better than assumed in the first draft of this plan,
which was wrong on this point.** Both `AuthService.refreshTokens()` and
`PortalAuthService.refreshTokens()` re-fetch the user after
`TokenService.rotateRefreshToken()` succeeds, and both already check
`isActive` — **a deactivated user's refresh is already refused today,
confirmed by reading the code directly, not assumed.** What's still
missing is the same gap as login: the consistency check is **link-field
based** (`user.applicantId || user.brokerId`), not role-based. A
staff-surface refresh for the exact unlinked-portal-role account shape
this release fixes at login would still succeed today. **Corrected in
this revision: the `role.isPortal` fix goes into both `refreshTokens()`
methods too, not just login/verify/admin-reset as the first draft had
it.** (The earlier draft's table entry calling this "no independent
check at all" and attributing a check at `auth.service.ts:258` to a
separate "JWT-strategy support lookup" was a misreading — that line is
inside `refreshTokens()` itself. Corrected below.)

**Q3 — is `roles.is_portal` changeable after creation, via UI or API?**

**No, confirmed by reading the schema directly.** Neither
`createRoleSchema` nor `updateRoleSchema` (`apps/api/src/roles/roles.dto.ts`)
has an `isPortal` field at all — `.strict()` on both means any attempt
to send one is rejected outright. A role's portal/staff nature is fixed
at creation (`is_portal Boolean @default(false)` in the schema) and
never changes after. Per the architect's own conditional instruction,
no matching guard on `roles.is_portal` changes is needed in Part C —
there's nothing to guard.

**Q4 — does the append-only trigger honour `app.allow_financial_mutation`
in production, and which roles can set it?**

Reported only, nothing changed, per instruction. The trigger function
(`forbid_financial_mutation()`) checks
`current_setting('app.allow_financial_mutation', true) = 'on'`
unconditionally — it has no environment check baked in, so it would
honour the setting in production exactly as it does in a test. **Grepped
every production path** (`apps/api/src`, `packages/db/src`,
`deploy/`) — **the GUC is never set anywhere outside
`apps/api/test/helpers/postsales-harness.ts`.** No production code or
deploy script sets it. Separately: **this is a plain custom GUC with no
role-level restriction defined anywhere in the migrations** — by
Postgres's default behaviour, *any* connected role, including
`openestate_app` (the ordinary, RLS-enforced role the live API uses for
every request), can run `SET app.allow_financial_mutation = 'on'`
within its own session or transaction. Nothing currently exercises this
capability, but the capability itself exists at the role level, not
just "nothing does it today." Reported as asked; no fix proposed here.

**The trigger — corrected for RLS-independence and fail-closed
behaviour.**

```sql
CREATE OR REPLACE FUNCTION forbid_unlinked_portal_role() RETURNS trigger
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, public
AS $$
DECLARE
  v_is_portal boolean;
BEGIN
  SELECT is_portal INTO v_is_portal FROM roles WHERE id = NEW.role_id;

  -- Fail CLOSED: if the role can't be resolved at all (a bad role_id, or
  -- — the case this SECURITY DEFINER + search_path exists to rule out —
  -- an RLS-visibility gap), refuse the write rather than silently
  -- allowing it through.
  IF v_is_portal IS NULL THEN
    RAISE EXCEPTION 'role_id % does not resolve to a known role', NEW.role_id;
  END IF;

  IF v_is_portal IS TRUE AND NEW.applicant_id IS NULL AND NEW.broker_id IS NULL THEN
    RAISE EXCEPTION 'A portal role requires an applicant_id or broker_id link';
  END IF;
  RETURN NEW;
END;
$$;

ALTER FUNCTION forbid_unlinked_portal_role() OWNER TO openestate_system;

CREATE TRIGGER users_forbid_unlinked_portal_role
  BEFORE INSERT OR UPDATE OF role_id, applicant_id, broker_id ON users
  FOR EACH ROW EXECUTE FUNCTION forbid_unlinked_portal_role();
```

**Why this shape, precisely:**
- **`SECURITY DEFINER` + `ALTER FUNCTION ... OWNER TO openestate_system`**
  — `openestate_system` is this project's existing `BYPASSRLS` role
  (created in the very first migration, `20260720000000_phase1_core`).
  A `SECURITY DEFINER` function runs with its *owner's* privileges, so
  the internal `SELECT ... FROM roles` always sees the role row
  regardless of the triggering session's own RLS context — including
  under a future `FORCE ROW LEVEL SECURITY` on `roles`, since
  `BYPASSRLS` overrides `FORCE RLS` unconditionally. This is the
  specific, named answer to "say which role works under FORCE RLS."
- **`SET search_path = pg_catalog, public`** (corrected from a bare
  `public`) — standard `SECURITY DEFINER` hardening: `pg_catalog` first
  ensures built-in types/operators can't be shadowed by an
  attacker-controlled object in `public` either, not just `roles`
  itself; pins the function's entire name resolution, not just the one
  table it happens to reference today.
- **`ALTER FUNCTION ... OWNER TO openestate_system` — confirmed to
  succeed in both environments that run migrations, not assumed.**
  Checked directly: `deploy/native/install-native.sh` runs migrations
  via `run_as_superuser`, connecting as the real `postgres` OS
  superuser (peer auth). CI's `scripts/test-setup.sh` creates and
  connects as `openestate_super`, explicitly declared
  `WITH LOGIN SUPERUSER`. **A Postgres superuser can always reassign
  ownership of any object, regardless of current ownership** — this
  isn't a permission that needs to be separately granted in either
  environment. No alternative needed.
- **Explicit `NULL` handling via `v_is_portal IS NULL` → `RAISE
  EXCEPTION`, never a bare `IF v_is_portal AND ...`** — a bare `IF NULL
  AND ...` evaluates to `NULL`, which Postgres's `IF` treats as false,
  silently *allowing* the write. That's the exact fail-open shape the
  architect flagged. The explicit `IS NULL` check up front means an
  unresolvable role always rejects, never silently passes.

**The migration's row-listing, and Part A's `NOT VALID` notices — both
corrected to not rely on `RAISE NOTICE` reaching anyone.** Per the
architect's Part-A correction (this applies identically here): whether
`prisma migrate deploy` forwards `NOTICE`-level output to its own
stdout in a way a log-grep would reliably catch was **not
independently confirmed**, and the safer design doesn't need to rely on
it either way. Both this migration's "list any pre-existing bad-state
users" step and Part A's "list any `NOT VALID` constraint" step move to
**a plain `SELECT` run by `upgrade-native.sh` itself, via `psql`, after
the migration completes** — not a notice emitted during the migration.
One new function in `deploy/native/lib.sh`,
`print_post_migrate_findings()`, runs two queries (bad-state users;
`NOT VALID` constraints) and prints a plain-English block for either
one that returns rows, called once from `upgrade-native.sh` right after
the migrate step, in both this release and v0.8.3.

**`SessionSurfaceGuard`'s pre-v0.8.1 fallback — corrected, OUT of
v0.8.2.** The earlier draft's "the window has already passed" claim was
wrong on the arithmetic: v0.8.1 shipped 2026-09-27, and its 7-day
staff-session window ends **2026-10-04**, not before — this plan
predates that date. Separately, an install that jumps straight from
v0.8.0 to v0.8.2 (skipping v0.8.1 as an intermediate step, which this
project's own upgrade path doesn't forbid) would still be carrying
tokens with no `surface` claim at all — the fallback is needed for
those regardless of elapsed time. **Removing the fallback is deferred
to v0.8.3**, with a release note that removal forces a one-time
re-login for any session whose token predates v0.8.1 (or any install
that upgraded straight from v0.8.0). The fallback stays exactly as it
is in v0.8.2 — untouched, not even revisited.

## F. Privilege escalation — expanded to "cannot act on or grant beyond
what you hold"

**Confirmed severity, per Q1 above: this is not a narrow gap.** A
`company_admin` can self-promote to `super_admin` in one request
(`PATCH` their own user, or `PATCH` their own role), or take over the
real `super_admin` account directly via `forcePasswordReset` (the
reset link is shown on screen) plus `resetTotp`. **Every one of these
is reachable through completely ordinary, already-shipped admin UI.**

**The principle, applied everywhere an admin acts on or grants
something:** the caller's own current permission set must be a
superset of whatever they're touching — either a target user's
*current* role's permissions, or the permission list they're about to
grant to a role.

**1. Target-user protection — `create`, `update`, `deactivate`,
`reactivate`, `forcePasswordReset`, `resetTotp` (`UsersService`).** Each
gains a check: load the target's *current* role's permission set
(for `update`, this is the target's role *before* any change in the
same request — the thing being protected is "can you touch this
account at all," independent of what you're changing it to), and
refuse unless the caller's own permission set is a superset. **`update`
gets a second check**, for the *new* role if one is being set: the
caller must also hold a superset of the *new* role's permissions (so a
`company_admin` can't launder an escalation by editing a role into
something narrower first, then back). **`super_admin` targets are
actionable — by any of these six operations — only by another
`super_admin`**, stated as an explicit rule alongside the subset check,
not relied upon to fall out of it implicitly (same reasoning as the
earlier draft's exception, now applied uniformly to all six operations
instead of just role assignment).

**2. No user may change their own role.** A new, simple check in
`update()`: if `userId === callerId` and `dto.roleId !== undefined`,
refuse outright — `BadRequestException('You cannot change your own
role.')`. This closes the most direct escalation path found (Q1) on
its own, independent of the subset check, so it holds even in a future
where the subset check has a bug.

**3. Role editing — `create`, `update`, and a new `deactivate` check
(`RolesService`) — applied universally, not scoped to
`admin.role.update`-holders only, per the architect's answer to the
open question this plan raised last round.** A caller cannot create a
role with, edit a role to hold, or deactivate a role holding any
permission the caller doesn't have — **including the caller's own
role.** This is the direct fix for the most severe path in Q1 (a
`company_admin` editing their own role to add every remaining
permission).

**4. Caller freshness — corrected and widened per the architect's
amendment.** Not just the permission list: **every check added in this
Part loads the caller fresh from the database by `req.user.sub`** —
current `roleId`, that role's current permissions, and `isActive` —
and trusts none of `roleId`/`permissions`/anything else from the JWT.
Two reasons this is wider than the original draft's "just re-fetch
permissions" framing:
- **Role staleness, not just permission staleness.** The original draft
  only worried about a *narrowed* role's stale permission list. A
  caller's *role itself* can change mid-session (reassigned to a
  different role entirely) — re-fetching permissions for the token's
  old `roleId` would silently check against the wrong role altogether.
  Loading the current `roleId` fresh, then that role's current
  permissions, closes both.
- **Deactivation.** If the caller's own account has been deactivated
  since they signed in (their access token can still be live for up to
  its remaining lifetime — the same JWT-staleness class this whole
  check exists to close), every one of these operations now **refuses
  outright** if the freshly-loaded caller is `isActive: false` —
  `ForbiddenException('Your account is no longer active.')` — rather
  than proceeding to evaluate a permission check for an account that
  shouldn't be acting at all.

**Extended test, per instruction:** the JWT-staleness test now covers
two scenarios, not one — (a) the caller's role is changed to a
*different* role mid-session (not just narrowed) and the next request
is checked against the new role, not the token's stale one; (b) the
caller's account is deactivated mid-session and the next request using
the still-valid access token is refused outright, before any
permission comparison runs.

**5. Lockout guard — new, per the architect's amendment.** `deactivate`,
and `update()` when it would change a `super_admin` user's role away
from `super_admin`, are refused if the operation would leave the
company with **zero active `super_admin` users**. Checked with a
`COUNT(*)` over active users holding the `super_admin` role in the
caller's own company, excluding the target row being acted on, done
inside the same transaction as the write (so a concurrent deactivation
of two different super_admins can't both pass the check and jointly
zero out the company — same "lock the row, check, then write" pattern
`assertValidManager`'s cycle check already uses elsewhere in this
file). This is deliberately narrower than a general "don't let the
company go admin-less" rule — it protects specifically against losing
the *top* role, which has no path back in except the CLI break-glass
script; a company with zero `company_admin`s but at least one
`super_admin` can always recover through the UI, so that case isn't
guarded here.

**6. Peer actions — explicitly allowed, stated as a deliberate
decision, per the architect's amendment.** The subset rule is
*"the caller's permissions must be a superset of the target's"* —
mathematically, a set is always a subset of itself. **A `company_admin`
acting on another `company_admin` (identical permission sets) is
therefore allowed by this rule as written, and that's intentional, not
an oversight.** Two administrators of equal standing being able to
manage each other's accounts is ordinary, expected admin behaviour
(covering for a colleague, offboarding a departing admin) — restricting
it would break real workflows this fix isn't meant to touch.
**Accountability for peer actions relies on the audit log**, not a
new restriction: every one of these six operations already writes (or,
for `forcePasswordReset`/`resetTotp`, already writes via
`RESET_LINK_ISSUED`/`TOTP_RESET_BY_ADMIN`) an audit row naming the
actor, so a peer-on-peer action is fully attributable after the fact
even though it isn't blocked beforehand.

**7. Wildcard grants must be expanded before comparing — with its own
test.** `company_admin`'s permission set in `ROLE_PERMISSIONS` is
stored as prefix filters (`admin.*`, `inventory.*`, etc.) at the
constant-definition level, but what lands in `role_permissions` (and
therefore what a database-driven check reads) is the **fully expanded,
literal list of permission keys** — the wildcard is a `roles.ts`
authoring convenience, resolved once at seed/sync time, never stored or
compared as a literal `"admin.*"` string. So the subset comparison is
naturally correct as a plain set-membership check against the
database rows — **the risk being tested for is a future regression**
where someone "optimizes" the check to compare against the constant
definitions directly instead of the database rows, silently
reintroducing wildcard-vs-literal mismatches. New test:
`apps/api/test/e2e-role-escalation.test.ts` asserts that a caller
holding `company_admin`'s real, expanded, database-stored permission
set is correctly treated as *not* a superset of `super_admin`'s
`portal.*` permissions — proving the comparison operates on expanded
lists, not prefix strings.

**8. Mirror-audit: portal-side admin actions
(`PortalAuthService.issueAdminPasswordReset`, `adminResetTotp`).**
Checked directly, per the standing mirrored-auth rule. Both take an
`applicantId`/`brokerId` as input, never a bare user id, and act on
whatever portal account matches — **there is no "target's role's
permission set" question here in the same sense**, because the only
roles a portal account can ever hold are `customer`/`broker`, which
carry only `portal.*` permissions, and the staff caller issuing these
already needs `ADMIN_PORTAL_INVITE_SEND` — a staff-only permission with
no `portal.*` overlap by construction. **No equivalent escalation
exists on the portal admin-action side** — confirmed by tracing both
functions directly, not assumed by symmetry with the staff side.

**Release note, exact content:** advise admins to review their list of
`super_admin`/`company_admin` users after upgrading, since any account
created or promoted via this gap before v0.8.2 would look completely
legitimate — same wording style as the SF-01 advisory.

**How it's tested:**
- `apps/api/test/e2e-role-escalation.test.ts` (new): covers all six
  `UsersService` operations against a `super_admin` target (each
  refused), the self-role-change refusal, all three `RolesService`

  edit would add anything beyond what the caller already holds), the

## Advisory impact and severity

**Verified first, as instructed: do `portal.*` permissions have any
effect for a staff-surface session?** No — confirmed by two direct
checks, not assumed. Every route that checks a `PORTAL_*` permission
(`grep`'d across `apps/api/src`: 7 controller files) is mounted under
the `portal/...` path prefix — zero exceptions found. `SessionSurfaceGuard`
refuses a staff-surface token on any portal-prefixed route before
`PermissionsGuard` is even reached, regardless of what permissions the
token's own `permissions` array claims to hold. **So a `super_admin`
account's `portal.*` permissions are structurally inert on a
staff-surface session** — they can never be exercised through the
staff login path this bug abuses.

**This changes the honest framing of one specific scenario, without
lowering the overall severity — worth stating precisely, not
glossed over:**
- A `company_admin` who takes over the real `super_admin`'s **staff**
  session gains **no new usable capability** beyond what `company_admin`
  already had — `company_admin` already holds every staff-side
  permission `super_admin` does; the only delta (`portal.*`) is unusable
  in that context. The real damage in *this specific* scenario is
  **impersonation and denial of service** (see below), not new access.
- **The worst case is a different starting point, and it's still
  severe: any custom staff role holding only a narrow user- or
  role-management permission** (e.g. `ADMIN_USER_UPDATE` alone, or
  `admin.role.update` alone — a deliberately scoped-down helpdesk-style
  account) **can use this exact bug to reach full `company_admin`-or-broader
  control across the entire staff permission surface** (`admin.*`,
  `inventory.*`, `presales.*`, `postsales.*`, `accounts.*`, `reports.*`)
  — a genuine, large capability gain, unrelated to the portal.*
  nuance above.

**Impact, framed as three distinct points, per instruction:**
1. **Impersonation/takeover of any same-or-lower account** — real for
   every pairing the subset rule doesn't block (including the
   deliberately-allowed peer case, item 6 above), with accountability
   resting on the audit log rather than prevention.
2. **Lockout of the real `super_admin`** — a `company_admin` (or any
   account holding `ADMIN_USER_UPDATE`) can deactivate every
   `super_admin` account in the company outright, a genuine denial-of-service
   against the top administrative role, with no capability delta
   needed to do it.
3. **Worst case: a narrowly-scoped custom role escalating to full
   tenant control** — the scenario above, the one that most clearly
   justifies the CVSS Integrity/Confidentiality impact staying at High.

**CVSS: kept at `AV:N/AC:L/PR:H/UI:N/S:U/C:H/I:H/A:H`, 7.2 — the
portal.* finding doesn't change it.** The worst-case scenario (point 3)
still reaches full read/write control of a tenant's entire non-portal
data surface, which is what `C:H`/`I:H` reflect; the `company_admin`→`super_admin`
scenario being capability-neutral doesn't lower the *ceiling* the CVSS
score is meant to capture. **Arithmetic, shown per the FIRST/NVD
calculator's own formula, not just asserted:**

```
Metric values (CVSS 3.1 base):
  AV:N = 0.85   AC:L = 0.77   PR:H (Scope Unchanged) = 0.27   UI:N = 0.85
  C:H = 0.56    I:H = 0.56    A:H = 0.56

ISCbase   = 1 - [(1-0.56) * (1-0.56) * (1-0.56)]
          = 1 - [0.44 * 0.44 * 0.44]
          = 1 - 0.085184
          = 0.914816

Impact (Scope Unchanged) = 6.42 * ISCbase
                          = 6.42 * 0.914816
                          = 5.87312   (rounded)

Exploitability = 8.22 * AV * AC * PR * UI
               = 8.22 * 0.85 * 0.77 * 0.27 * 0.85
               = 8.22 * 0.85  = 6.987
                 6.987 * 0.77 = 5.380
                 5.380 * 0.27 = 1.4526
                 1.4526 * 0.85 = 1.2347

BaseScore (Scope Unchanged) = Roundup( Min[ Impact + Exploitability, 10 ] )
                             = Roundup( Min[ 5.87312 + 1.2347, 10 ] )
                             = Roundup( 7.10782 )
                             = 7.2
```

**7.2 — High.** (For reference, not adopted: substituting `PR:L`
instead of `PR:H` — i.e. treating `company_admin` as only "basic user"
privilege rather than "significant" — moves this to 8.8, still High,
just below the 9.0 Critical threshold. `PR:H` is kept as the more
accurate read, since `company_admin` is this app's own tenant-wide
administrative role, not a basic-capability one.) This hand
calculation should still be run through the actual FIRST/NVD calculator
before it goes into the published advisory, as a final check, not a
replacement for one.
