# v0.8.3 — database integrity release: plan only

**Status: plan for approval. Nothing described here has been built.**
This document is intentionally not committed. Split from the original
combined plan, per the architect's decision: v0.8.2 (security fixes)
ships first, on its own branch and PR; this file — Parts A and B, the
71 missing foreign keys and the CI guards that stop it recurring —
ships second, as v0.8.3, also its own branch and PR.

## For the owner, in plain words

A migration written back in the product's early days (`v0.2.0`, August
2026) removed 71 safety checks from the database by accident — the kind
that stop a row from pointing at a user, a rate, or a record that
doesn't exist. It happened because an automated tool doesn't know about
a small number of checks this project adds by hand outside its normal
schema file, so it saw them as "extra" and proposed deleting them;
whoever reviewed that change didn't catch it among dozens of
routine-looking lines. Every release since has been missing them.

The good news, confirmed twice, independently: the ledger's own
tamper-proofing (a financial row can never be edited or deleted once
written) was never touched, on any of the 71. A real check against your
own server found zero rows anywhere pointing at something that doesn't
exist. This is a real gap, worth closing properly, but it has not
corrupted anything on your install.

This release adds the 71 checks back, safely, and builds the tooling so
the same mistake can't happen silently again.

---

## A. Restoring the 71 foreign keys — corrected

**What changes — unchanged in shape from the previous draft: `NOT
VALID` + `VALIDATE CONSTRAINT` inside an exception-catching block, no
`UPDATE`/`DELETE` on any row, no trigger touched.** One correction,
below, to how a validation failure is surfaced to the admin.

**Corrected: do not rely on `RAISE NOTICE` reaching anyone.** The
previous draft had the migration's own `DO $$ ... EXCEPTION ...`
block `RAISE NOTICE` the name of any constraint that fails to validate,
assuming `upgrade-native.sh`'s existing log-grep would catch it.
**Whether `prisma migrate deploy` forwards Postgres `NOTICE`-level
output into its own process's stdout — where `MIGRATE_LOG`'s `tee`
could see it — was not independently confirmed, and doesn't need to
be**, because there's a strictly more reliable design available
regardless of the answer: **`upgrade-native.sh` runs a plain `SELECT`
against `pg_constraint` itself, via `psql`, immediately after the
migration completes** — `SELECT conname, conrelid::regclass FROM
pg_constraint WHERE NOT convalidated AND conname = ANY($1)` (the 71
names, or a `contype = 'f' AND connamespace = 'public'::regnamespace`
scan more broadly, to also catch anything unexpected). This is the
same `print_post_migrate_findings()` function introduced in v0.8.2 for
the equivalent "list bad-state users" step — this migration's own
finding is the second caller of that same function, not a new
mechanism.

**Everything else from the previous draft stands unchanged:** the
migration itself never writes to a row; the constraint stays `NOT
VALID` (still enforcing new writes) rather than the whole migration
failing; a clean install (confirmed on the maintainers' own VM)
validates all 71 silently.

**Files:**
- `packages/db/prisma/migrations/<ts>_restore_dropped_foreign_keys/migration.sql` (new)
- `deploy/native/lib.sh` (`print_post_migrate_findings()` — shared with
  v0.8.2, so this release's branch either rebases on v0.8.2's merged
  function or, if v0.8.3 is cut before v0.8.2 merges, adds its own
  second caller to the same function name, reconciled at merge time)
- `deploy/native/upgrade-native.sh` (call the FK-validation check after
  this migration)

**How it's tested:**
- `packages/db/test/restore-foreign-keys.test.ts`: migrates a fresh
  test database, queries `pg_constraint`, asserts all 71 are present
  and `convalidated = true`.
- A second test builds a pre-migration orphan row (via the
  `app.allow_financial_mutation` test-only escape hatch), runs the
  migration, and asserts: no throw, the specific constraint comes back
  `convalidated = false`, every other constraint is valid, the orphan
  row is untouched.
- A new test for the corrected surfacing mechanism itself:
  `print_post_migrate_findings()` run against a database with one
  deliberately `NOT VALID` constraint returns non-empty output naming
  it; run against an all-valid database returns nothing.
- CI's `native-upgrade-from-populated-DB` job asserts the upgrade log
  is clean (no findings) on its own known-orphan-free fixture.

**Risk:** low. Same reasoning as the original draft; the correction
only changes *how* a finding is surfaced, not the safety of the
underlying migration.

## B. Stopping this from happening again — corrected

**Correction 1: the lint cannot apply to historical migrations.**
Migration files that have already been applied on any real install are
checksummed by Prisma — editing one (even just adding a comment) breaks
that checksum and fails every existing install's next `migrate deploy`.
The suspect migration alone has ~78 unmarked `DROP CONSTRAINT` lines;
retroactively marking them is not an option.

**Fix: the lint script has a fixed cutoff, recorded as a constant in
the script itself, not inferred.** Every migration up to and including
`20260927120000_portal_broker_dashboard_permission` (the most recent
migration as of `master`/v0.8.1, before either this release or v0.8.2
adds anything new) is exempt — the lint skips any migration directory
whose name sorts at or before this cutoff. Every migration *after* it —
starting with v0.8.2's and v0.8.3's own new migrations — is linted in
full, per the original rule (`DROP CONSTRAINT`/`DROP TRIGGER`/`DROP
POLICY` needs an `-- ALLOW-DROP: <reason>` comment with a non-empty
reason, or CI fails, naming the file and line). The cutoff constant is
a single, clearly-commented line at the top of the lint script,
explaining exactly why it exists and pointing at this investigation —
so a future contributor doesn't mistake it for an arbitrary magic
string.

**Correction 2: the manifest generator is pinned to PostgreSQL 16 and
normalises policy-expression text.** Two real flake sources, closed
before they cause one:
- **PostgreSQL version pin.** `pg_get_constraintdef()` and RLS policy
  expression formatting can differ in minor, cosmetic ways across
  Postgres versions (whitespace, implicit cast notation). The generator
  script and the CI test that compares against it both run against the
  exact same pinned image — **`postgres:16-alpine`**, matching this
  project's already-stated stack version (CLAUDE.md: "PostgreSQL 16
  (RLS enabled)") — not "whatever Postgres happens to be installed."
- **Expression normalisation.** Before writing (and before comparing)
  a `USING`/`WITH CHECK` expression or a constraint definition string,
  both the generator and the CI test pass it through the same small
  normalisation step (collapse whitespace, lowercase keyword casing to
  match Postgres's own canonical `pg_get_*def()` output rather than
  re-deriving a separate style) — so a run on a different machine or a
  different Postgres point release doesn't fail the comparison over
  formatting that carries no semantic difference.

**Everything else from the previous draft stands:** the manifest is
generated (not hand-typed), captures foreign keys, unique constraints,
check constraints, triggers, RLS policies (`pg_policies`: name, table,
command, permissive/restrictive, `USING`/`WITH CHECK`), and each
table's `relrowsecurity`/`relforcerowsecurity` flags; a dropped or
altered policy fails CI exactly like a dropped foreign key; the missing
"insert a bad reference, assert Postgres rejects it" test class is
generated from the manifest, one test per enforced foreign key; the
CLAUDE.md rule is added, now also naming `DROP POLICY` alongside
`DROP CONSTRAINT`/`DROP TRIGGER`.

**Files:**
- `packages/db/scripts/generate-constraint-manifest.ts` (new — pinned
  to `postgres:16-alpine`, normalises expression text)
- `packages/db/constraint-manifest.json` (new, generated, committed)
- `packages/db/test/constraint-manifest.test.ts` (new — same pin, same
  normalisation, so it compares like-for-like against the manifest)
- `apps/api/test/e2e-fk-enforcement.test.ts` (new)
- `.github/workflows/ci.yml` (new lint step + manifest-check step,
  both pinned to the same Postgres version the rest of CI already uses)
- `scripts/lint-migration-drops.<ext>` (new — the cutoff-aware lint,
  exact name/language TBD, likely matching whatever the repo's other
  small CI lint scripts are already written in)
- `CLAUDE.md` (new rule, naming all three drop types)

**How it's tested:**
- The manifest test and the FK-enforcement tests are themselves the
  coverage.
- The lint is proven three ways in a throwaway scratch commit,
  reverted after: an unmarked drop *after* the cutoff fails; an
  unmarked drop *at or before* the cutoff (simulated by temporarily
  lowering the constant, never by editing a real historical file)
  passes, proving the cutoff logic itself; a marked drop with an empty
  `-- ALLOW-DROP:` reason fails the same as no marker.
- The Postgres-version pin and normalisation are proven by running the
  generator and the CI test against two different real Postgres 16.x
  point releases (whatever two are readily available) and confirming
  identical manifest output — the actual failure mode being guarded
  against, not just asserted away.

**Risk:** low for the manifest/tests (additive, no runtime change). The
cutoff constant is the one piece of this that must be exactly right —
verified by confirming it names the true most-recent migration as of
`master` at the time this plan was written, not assumed.

## G. Harden the append-only escape hatch

**Why this is here, not in v0.8.2:** it's a database-hardening change
in the same family as Parts A/B (a GUC-and-trigger mechanism, not an
application authorization check), and it's not urgent the way v0.8.2's
findings are — per Q4's own answer, nothing in production code
currently sets this GUC at all. Worth closing properly, not urgently.

**The gap, restated from Q4.** `app.allow_financial_mutation` is a
plain custom Postgres GUC with no role-level restriction defined
anywhere. `forbid_financial_mutation()` only checks whether the setting
is `'on'` — it never checks *who* set it. By Postgres's default
behaviour, any connected role — including `openestate_app`, the
ordinary RLS-enforced role the live API uses for every request, and
`openestate_system` — can run `SET app.allow_financial_mutation = 'on'`
in their own session or transaction and the trigger would honour it.
Nothing exercises this today (confirmed by grep, Q4), but the
capability shouldn't exist at all for the roles a running install
actually uses.

**The fix.** A new, dedicated Postgres role,
`openestate_maintenance` — `NOLOGIN` by default in a real install
(matching this project's existing pattern for roles that exist as a
permission boundary, not a connectable account; it's granted `LOGIN`
only where something legitimately needs to assume it, the same
"enable LOGIN and set a password before use" pattern
`openestate_system`'s own creation comment already documents). The
trigger function changes from checking only the GUC to checking both
the GUC **and** the connected role:

```sql
CREATE OR REPLACE FUNCTION forbid_financial_mutation() RETURNS trigger AS $$
BEGIN
  IF current_setting('app.allow_financial_mutation', true) = 'on'
     AND current_user = 'openestate_maintenance' THEN
    IF TG_OP = 'DELETE' THEN RETURN OLD; ELSE RETURN NEW; END IF;
  END IF;
  RAISE EXCEPTION 'Table % is append-only; % is not permitted', TG_TABLE_NAME, TG_OP
    USING HINT = 'Financial rows are immutable; post a reversal entry instead.';
END;
$$ LANGUAGE plpgsql;
```

`current_user` is the role actually executing the statement in that
session — not the function's owner (this function is intentionally
**not** `SECURITY DEFINER`; the opposite property is wanted here from
Part C's trigger, which needs to see privileged data regardless of the
caller — this one needs to see *who the caller genuinely is* and
refuse to be fooled by an owner's identity). Setting the GUC alone is
no longer sufficient for any role except the one dedicated maintenance
role — `openestate_app` and `openestate_system` both lose the
capability entirely, even if a future bug or injection ever got either
of them to attempt the `SET`.

**What has to change alongside it:** the one legitimate consumer of
this escape hatch — `apps/api/test/helpers/postsales-harness.ts`'s test
teardown — needs its cleanup connection to assume `openestate_maintenance`
specifically (via `SET ROLE` or a dedicated connection string), not
whatever role it currently connects as for teardown. `deploy/native/setup-database.sh`
gains the new role's creation, alongside the existing
`openestate_app`/`openestate_system` setup.

**Files:**
- `packages/db/prisma/migrations/<ts>_scope_financial_mutation_escape_hatch/migration.sql`
  (new — creates `openestate_maintenance`, replaces the trigger
  function)
- `deploy/native/setup-database.sh` (create the new role on every
  install, alongside the existing two)
- `apps/api/test/helpers/postsales-harness.ts` (teardown assumes the
  new role explicitly)
- `scripts/test-setup.sh` (grant the new role to whichever role runs
  test teardown, so `SET ROLE openestate_maintenance` succeeds)

**How it's tested:**
- The direct proof requested: a new test connects as `openestate_app`
  (the real, ordinary, RLS-enforced application role — not a test-only
  superuser), sets `app.allow_financial_mutation = 'on'` in its own
  session, and attempts an `UPDATE`/`DELETE` on `ledger_entries` — **the
  trigger still refuses it**, proving the GUC alone is no longer
  enough. A companion test does the identical thing as
  `openestate_system` (`BYPASSRLS` but, after this fix, still not the
  maintenance role) and gets the same refusal — proving `BYPASSRLS`
  and "may bypass the append-only trigger" are no longer the same
  thing.
- A positive test: connecting as `openestate_maintenance` with the GUC
  set succeeds, exactly as the escape hatch has always worked for
  legitimate test teardown.
- The existing test-suite teardown itself is the regression check that
  the role-reassignment didn't break normal test cleanup — a full
  `pnpm test` run after this change is part of this PR's own
  verification, not a separate task.

**Risk:** low. Purely additive at the database-role level; the one
real behavioural change (test teardown must assume a specific role) is
exercised by every single test file's own teardown running under CI,
so a mistake here fails loudly and immediately, not silently.
