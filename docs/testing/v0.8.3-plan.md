## For the owner, in plain words

A migration written back in the product's early days (`v0.2.0`, August
2026) removed 71 safety checks from the database by accident — the kind
that stop a row from pointing at a user, a rate, or a record that
doesn't exist. It happened because an automated tool doesn't know about
a small number of checks this project adds by hand outside its normal
schema file, so it saw them as "extra" and proposed deleting them;
whoever reviewed that change didn't catch it among dozens of
routine-looking lines. Every release since has been missing them.

The good news, confirmed twice, independently: the ledger's own
tamper-proofing (a financial row can never be edited or deleted once
written) was never touched, on any of the 71. A real check against your
own server found zero rows anywhere pointing at something that doesn't
exist. This is a real gap, worth closing properly, but it has not
corrupted anything on your install.

This release adds the 71 checks back, safely, and builds the tooling so
the same mistake can't happen silently again.

## A. Restoring the 71 foreign keys — corrected

**What changes — unchanged in shape from the previous draft: `NOT
VALID` + `VALIDATE CONSTRAINT` inside an exception-catching block, no
`UPDATE`/`DELETE` on any row, no trigger touched.** One correction,
below, to how a validation failure is surfaced to the admin.

**Corrected: do not rely on `RAISE NOTICE` reaching anyone.** The
previous draft had the migration's own `DO $$ ... EXCEPTION ...`
block `RAISE NOTICE` the name of any constraint that fails to validate,
assuming `upgrade-native.sh`'s existing log-grep would catch it.
**Whether `prisma migrate deploy` forwards Postgres `NOTICE`-level
output into its own process's stdout — where `MIGRATE_LOG`'s `tee`
could see it — was not independently confirmed, and doesn't need to
be**, because there's a strictly more reliable design available
regardless of the answer: **`upgrade-native.sh` runs a plain `SELECT`
against `pg_constraint` itself, via `psql`, immediately after the
migration completes** — `SELECT conname, conrelid::regclass FROM
pg_constraint WHERE NOT convalidated AND conname = ANY($1)` (the 71
names, or a `contype = 'f' AND connamespace = 'public'::regnamespace`
scan more broadly, to also catch anything unexpected). This is the
same `print_post_migrate_findings()` function introduced in v0.8.2 for
the equivalent "list bad-state users" step — this migration's own
finding is the second caller of that same function, not a new
mechanism.

**Everything else from the previous draft stands unchanged:** the
migration itself never writes to a row; the constraint stays `NOT
VALID` (still enforcing new writes) rather than the whole migration
failing; a clean install (confirmed on the maintainers' own VM)
validates all 71 silently.

**Files:**
- `packages/db/prisma/migrations/<ts>_restore_dropped_foreign_keys/migration.sql` (new)
- `deploy/native/lib.sh` (`print_post_migrate_findings()` — already on
  `master` since v0.8.2; this is its second caller)
- `deploy/native/upgrade-native.sh` (call the FK-validation check after
  this migration)

**How it's tested:**
- `packages/db/test/restore-foreign-keys.test.ts`: migrates a fresh
  test database, queries `pg_constraint`, asserts all 71 are present
  and `convalidated = true`.
- A second test builds a pre-migration orphan row (via the
  `app.allow_financial_mutation` test-only escape hatch, **using the
  Part G maintenance role, so Part G ships first**), runs the
  migration, and asserts: no throw, the specific constraint comes back
  `convalidated = false`, every other constraint is valid, the orphan
  row is untouched.
- A new test for the corrected surfacing mechanism itself:
  `print_post_migrate_findings()` run against a database with one
  deliberately `NOT VALID` constraint returns non-empty output naming
  it; run against an all-valid database returns nothing.
- CI's `native-upgrade-from-populated-DB` job asserts the upgrade log
  is clean (no findings) on its own known-orphan-free fixture.

**Risk:** low. Same reasoning as the original draft; the correction
only changes *how* a finding is surfaced, not the safety of the
underlying migration.

**Decided (2026-10-07): fail fast.** If the migration cannot take its locks
within the existing 15-second `lock_timeout`, the upgrade stops, the previous
release keeps running, and `upgrade-native.sh` prints a plain message: the
database was busy, nothing was changed, and the admin should run the upgrade
again at a quiet time (for example outside office hours). No automatic retry.

## B. Stopping this from happening again — corrected

**Correction 1: the lint cannot apply to historical migrations.**
Migration files that have already been applied on any real install are
checksummed by Prisma — editing one (even just adding a comment) breaks
that checksum and fails every existing install's next `migrate deploy`.
The suspect migration alone has ~78 unmarked `DROP CONSTRAINT` lines;
retroactively marking them is not an option.

**Fix: the lint script has a fixed cutoff, recorded as a constant in
the script itself, not inferred.** Every migration up to and including
`20260927120000_portal_broker_dashboard_permission` (the most recent
migration as of `master`/v0.8.1, before either this release or v0.8.2
adds anything new) is exempt — the lint skips any migration directory
whose name sorts at or before this cutoff. Every migration *after* it —
starting with v0.8.2's and v0.8.3's own new migrations — is linted in
full, per the original rule (`DROP CONSTRAINT`/`DROP TRIGGER`/`DROP
POLICY` needs an `-- ALLOW-DROP: <reason>` comment with a non-empty
reason, or CI fails, naming the file and line). The cutoff constant is
a single, clearly-commented line at the top of the lint script,
explaining exactly why it exists and pointing at this investigation —
so a future contributor doesn't mistake it for an arbitrary magic
string.

**Decided (2026-10-07): the cutoff is the last migration on `master` at the
moment Part B merges**, recorded by name in the lint script with a comment
saying why. It is not fixed in this plan, because Part S and the v0.8.3
migrations land before Part B.

**Correction 2: the manifest generator is pinned to PostgreSQL 16 and
normalises policy-expression text.** Two real flake sources, closed
before they cause one:
- **PostgreSQL version pin.** `pg_get_constraintdef()` and RLS policy
  expression formatting can differ in minor, cosmetic ways across
  Postgres versions (whitespace, implicit cast notation). The generator
  script and the CI test that compares against it both run against the
  exact same pinned image — **`postgres:16-alpine`**, matching this
  project's already-stated stack version (CLAUDE.md: "PostgreSQL 16
  (RLS enabled)") — not "whatever Postgres happens to be installed."
- **Expression normalisation.** Before writing (and before comparing)
  a `USING`/`WITH CHECK` expression or a constraint definition string,
  both the generator and the CI test pass it through the same small
  normalisation step (collapse whitespace, lowercase keyword casing to
  match Postgres's own canonical `pg_get_*def()` output rather than
  re-deriving a separate style) — so a run on a different machine or a
  different Postgres point release doesn't fail the comparison over
  formatting that carries no semantic difference.

**Everything else from the previous draft stands:** the manifest is
generated (not hand-typed), captures foreign keys, unique constraints,
check constraints, triggers, RLS policies (`pg_policies`: name, table,
command, permissive/restrictive, `USING`/`WITH CHECK`), and each
table's `relrowsecurity`/`relforcerowsecurity` flags; a dropped or
altered policy fails CI exactly like a dropped foreign key; the missing
"insert a bad reference, assert Postgres rejects it" test class is
generated from the manifest, one test per enforced foreign key; the
CLAUDE.md rule is added, now also naming `DROP POLICY` alongside
`DROP CONSTRAINT`/`DROP TRIGGER`.

**Files:**
- `packages/db/scripts/generate-constraint-manifest.ts` (new — pinned
  to `postgres:16-alpine`, normalises expression text)
- `packages/db/constraint-manifest.json` (new, generated, committed)
- `packages/db/test/constraint-manifest.test.ts` (new — same pin, same
  normalisation, so it compares like-for-like against the manifest)
- `apps/api/test/e2e-fk-enforcement.test.ts` (new)
- `.github/workflows/ci.yml` (new lint step + manifest-check step,
  both pinned to the same Postgres version the rest of CI already uses)
- `scripts/lint-migration-drops.<ext>` (new — the cutoff-aware lint,
  exact name/language TBD, likely matching whatever the repo's other
  small CI lint scripts are already written in)
- `CLAUDE.md` (new rule, naming all three drop types)

**How it's tested:**
- The manifest test and the FK-enforcement tests are themselves the
  coverage.
- The lint is proven three ways in a throwaway scratch commit,
  reverted after: an unmarked drop *after* the cutoff fails; an
  unmarked drop *at or before* the cutoff (simulated by temporarily
  lowering the constant, never by editing a real historical file)
  passes, proving the cutoff logic itself; a marked drop with an empty
  `-- ALLOW-DROP:` reason fails the same as no marker.
- The Postgres-version pin and normalisation are proven by running the
  generator and the CI test against two different real Postgres 16.x
  point releases (whatever two are readily available) and confirming
  identical manifest output — the actual failure mode being guarded
  against, not just asserted away.

**Risk:** low for the manifest/tests (additive, no runtime change). The
cutoff constant is the one piece of this that must be exactly right —
verified by confirming it names the true most-recent migration as of
`master` at the time this plan was written, not assumed.

## G. Harden the append-only escape hatch

**Why this is here, not in v0.8.2:** it's a database-hardening change
in the same family as Parts A/B (a GUC-and-trigger mechanism, not an
application authorization check), and it's not urgent the way v0.8.2's
findings are — per Q4's own answer, nothing in production code
currently sets this GUC at all. Worth closing properly, not urgently.

**The gap, restated from Q4.** `app.allow_financial_mutation` is a
plain custom Postgres GUC with no role-level restriction defined
anywhere. `forbid_financial_mutation()` only checks whether the setting
is `'on'` — it never checks *who* set it. By Postgres's default
behaviour, any connected role — including `openestate_app`, the
ordinary RLS-enforced role the live API uses for every request, and
`openestate_system` — can run `SET app.allow_financial_mutation = 'on'`
in their own session or transaction and the trigger would honour it.
Nothing exercises this today (confirmed by grep, Q4), but the
capability shouldn't exist at all for the roles a running install
actually uses.

**The fix.** A new, dedicated Postgres role,
`openestate_maintenance` — `NOLOGIN` by default in a real install
(matching this project's existing pattern for roles that exist as a
permission boundary, not a connectable account; it's granted `LOGIN`
only where something legitimately needs to assume it, the same
"enable LOGIN and set a password before use" pattern
`openestate_system`'s own creation comment already documents). The
trigger function changes from checking only the GUC to checking both
the GUC **and** the connected role:

```sql
CREATE OR REPLACE FUNCTION forbid_financial_mutation() RETURNS trigger AS $$
BEGIN
  IF current_setting('app.allow_financial_mutation', true) = 'on'
     AND current_user = 'openestate_maintenance' THEN
    IF TG_OP = 'DELETE' THEN RETURN OLD; ELSE RETURN NEW; END IF;
  END IF;
  RAISE EXCEPTION 'Table % is append-only; % is not permitted', TG_TABLE_NAME, TG_OP
    USING HINT = 'Financial rows are immutable; post a reversal entry instead.';
END;
$$ LANGUAGE plpgsql;
```

`current_user` is the role actually executing the statement in that
session — not the function's owner (this function is intentionally
**not** `SECURITY DEFINER`; the opposite property is wanted here from
Part C's trigger, which needs to see privileged data regardless of the
caller — this one needs to see *who the caller genuinely is* and
refuse to be fooled by an owner's identity). Setting the GUC alone is
no longer sufficient for any role except the one dedicated maintenance
role — `openestate_app` and `openestate_system` both lose the
capability entirely, even if a future bug or injection ever got either
of them to attempt the `SET`.

**What has to change alongside it:** the one legitimate consumer of
this escape hatch — `apps/api/test/helpers/postsales-harness.ts`'s test
teardown — needs its cleanup connection to assume `openestate_maintenance`
specifically (via `SET ROLE` or a dedicated connection string), not
whatever role it currently connects as for teardown. `deploy/native/setup-database.sh`
gains the new role's creation, alongside the existing
`openestate_app`/`openestate_system` setup.

**Files:**
- `packages/db/prisma/migrations/<ts>_scope_financial_mutation_escape_hatch/migration.sql`
  (new — creates `openestate_maintenance`, replaces the trigger
  function)
- `deploy/native/setup-database.sh` (create the new role on every
  install, alongside the existing two)
- `apps/api/test/helpers/postsales-harness.ts` (teardown assumes the
  new role explicitly)
- `apps/api/scripts/portal-demo-seed.ts` (the only other user of the
  setting; moves to the same role)
- `scripts/test-setup.sh` (grant the new role to whichever role runs
  test teardown, so `SET ROLE openestate_maintenance` succeeds)

**How it's tested:**
- The direct proof requested: a new test connects as `openestate_app`
  (the real, ordinary, RLS-enforced application role — not a test-only
  superuser), sets `app.allow_financial_mutation = 'on'` in its own
  session, and attempts an `UPDATE`/`DELETE` on `ledger_entries` — **the
  trigger still refuses it**, proving the GUC alone is no longer
  enough. A companion test does the identical thing as
  `openestate_system` (`BYPASSRLS` but, after this fix, still not the
  maintenance role) and gets the same refusal — proving `BYPASSRLS`
  and "may bypass the append-only trigger" are no longer the same
  thing.
- A positive test: connecting as `openestate_maintenance` with the GUC
  set succeeds, exactly as the escape hatch has always worked for
  legitimate test teardown.
- The existing test-suite teardown itself is the regression check that
  the role-reassignment didn't break normal test cleanup — a full
  `pnpm test` run after this change is part of this PR's own
  verification, not a separate task.

**Risk:** low. Purely additive at the database-role level; the one
real behavioural change (test teardown must assume a specific role) is
exercised by every single test file's own teardown running under CI,
so a mistake here fails loudly and immediately, not silently.

## H. End a session when the user is deactivated (UA-116) — plan only

**Problem.** Deactivating a user (or changing their role) revokes their
refresh token, but an access token they already hold keeps working until
it expires (`JWT_ACCESS_EXPIRES_IN`, 15 minutes by default), because the
JWT check never looks at the database. The UI audit (Phase 5a) showed a
deactivated sales user, still signed in, reading data and creating an
enquiry (201) after deactivation. This is the documented "Session
lifetime" trade-off in CLAUDE.md, not a hidden flaw, but it is wider than
an operator expects from "Deactivate".

**Already in place.** Since v0.8.2 every user/role admin action loads the
caller fresh from the database (`loadCurrentCaller`), so a demoted or
deactivated admin cannot use an old token for those actions. Ordinary
reads and writes (enquiries, receipts, bookings) do not.

**Proposed fix.** A global check, after `JwtAuthGuard`, that the token's
user is still active and still has the role (and permission set version)
the token was issued with. To avoid a database read per request, cache
`{isActive, roleId, permsVersion}` per user in Redis with a short TTL
(e.g. 30-60 s), and delete the cache entry on deactivate, reactivate,
role change and role-permission change. A cache miss reads the database;
a mismatch returns 401 so the client re-authenticates (and refresh then
fails for an inactive user). Staff and portal surfaces both, per the
mirrored-auth rule.

**Decided (2026-10-07).** Invalidate the cache **explicitly, write-through**,
on deactivate, reactivate, role change and role-permission change, so the
window after any of those is effectively zero. The 30-60 s TTL is a backstop
only, never the mechanism. If Redis is unreachable, fall back to a database
read; never fail open. Tests must cover all three: an explicit invalidation
takes effect on the very next request, the TTL backstop on its own, and the
Redis-down fallback (mutation-checked: with the fallback removed, a request
during a Redis outage must not be allowed through).

**Tests.** Mutation-checked: with the check removed, the "old token after
deactivation" test must fail. Through-the-wire: deactivate a user and confirm their very
next request with the old access token is 401; change a role's
permissions and confirm the next request is checked against the new set;
cache invalidation tested by forcing the interleaving (standing rule on
concurrency tests). A Playwright scenario with two browser contexts
(admin deactivates, the other context's next click is refused).

**Risk.** Medium: it touches every request. Needs a measured latency
check and a fail-closed decision if Redis is down (proposal: fall back to
a database read, never to "allow").

## I. Prerequisite: safe sync of seeded system-role permissions (UA-106)

**Problem.** Upgrades sync permission rows and super_admin's grants, but
never the other seeded system roles (company_admin, sales_manager,
sales_executive, accounts, customer, broker). So any fix that changes a
seeded role (for example giving accounts the broker access it needs to
pay commission, UA-105) reaches fresh installs only. The audit VM's
Accounts role already differs from a fresh install (33 vs 34 permissions;
no `admin.master.read`).

**Proposed fix.** An upgrade step that ADDS seeded permissions a system
role is missing, and never removes anything. Removal of a grant by an
admin is never undone silently.

**Design question to settle first: "admin removed it on purpose" vs
"never had it".** The database cannot tell these apart today. Options:
1. Record a per-role "seed baseline" (which seeded permissions the role
   was last synced to). A key in the new seed but not in the baseline is
   new and gets added; a key in the baseline but missing from the role
   was removed by an admin and is left alone. Needs one new table or a
   JSON column, and an initial baseline captured on the first upgrade
   (from the current grants, so nothing an admin removed is resurrected).
2. Only add keys introduced after a given release, listed explicitly in
   the release (a "grants added in vX" manifest). Simpler, no baseline,
   but every release that changes a seeded role must remember to write
   the manifest.
3. Never auto-add; print a report after upgrade listing the difference
   between each system role and its seed, for the admin to apply in the
   Roles screen. Safest, but relies on the operator acting.
Recommendation: option 1, with option 3's report printed as well, and
the same audit row (`ROLE_PERMS_CHANGED`) the v0.8.2 role update writes.

**Decided (2026-10-07): per-role seed baseline + report.** On an install
with no baseline (every existing install), the first upgrade auto-adds
**nothing**: it records the baseline and prints a report of seeded-vs-actual
differences per system role, and the admin decides in the Roles screen. Later
releases auto-add only permissions newly introduced to a role's seed after its
recorded baseline. A permission an admin removed is never re-added. Each
auto-add writes a `ROLE_PERMS_CHANGED` audit row. Tests: a first upgrade with
differences adds nothing and prints them; a later seed addition arrives; an
admin removal stays removed (all outcome assertions, mutation-checked).

**Tests.** (Mutation check: with the sync step removed the "added one arrives" assertion must fail.) Upgrade from a baseline where an admin removed one seeded
permission and the seed added another: assert the added one arrives, the
removed one stays removed (outcome assertion, per the standing rule).

## J. Upgrade-script fix: tag fetch fails on clones made before the history rewrite

**Problem (known, documented in the v0.8.2 release notes).** `upgrade-native.sh`
runs `git fetch --tags && git checkout "$REF"` (inside `set -e`). On a clone
made before the history rewrite, local tags `v0.1.0` to `v0.7.1` point at old
commits; git refuses to overwrite them ("would clobber existing tag") and the
script exits silently after its backup. Nothing changed, nothing was printed
by us. Workaround today: `git fetch --tags --force origin`, then re-run.

**Fix.** Fetch only what was asked for, force it, and say so when it fails:
- Replace the line with a fetch of the single requested ref (`git fetch --force
  origin "$REF"` for a tag, branch or commit; tags fetched as
  `refs/tags/$REF:refs/tags/$REF`), then `git checkout --detach FETCH_HEAD` or
  the tag. Never fetch all tags.
- Check the fetch's exit status explicitly and `die` with the git error text and
  a one-line hint. No reliance on `set -e` propagation (the project has been
  bitten by that before).
- A fetch failure must stop the upgrade before any build, and print that the
  previous release is untouched.

**Limit, stated plainly.** A fixed script cannot help an install that runs its
old one: the first upgrade on an affected clone still needs the manual
`fetch --tags --force`. The release notes keep that workaround.

**Decided (2026-10-07):** the installation-guide note is enough for the
first upgrade on an affected clone; the fixed script handles every upgrade from
v0.8.3 on. No installer check for diverged tags.

**Files:** `deploy/native/upgrade-native.sh`; `.github/workflows/ci.yml`
(or the existing native-upgrade job's script) for the new test.

**Tests.** A CI test with a **diverged local tag**: create a bare "origin"
repo, tag `vX` at commit 1, clone it, then move the origin's `vX` to commit 2;
run the upgrade's fetch step and assert the clone ends at commit 2 and the
script exits 0. A second case: an unreachable origin must exit non-zero with
the clear error. Mutation check: with the old `git fetch --tags` line the first
case must fail (and does today).

**Risk:** low. Size: S.

## K. UA-110: audit timestamps written as UTC

**Problem (root cause confirmed read-only).** `audit_logs.created_at` is
`TIMESTAMP(3)` without time zone and the app treats every such column as UTC.
The generic audit extension (`packages/db/src/audit.extension.ts`, the raw
`INSERT ... NOW()` at line 206) lets Postgres fill the value, which stores the
session's local clock. On a server whose Postgres time zone is not UTC (the test
VM runs Asia/Kolkata) every generic CREATE/UPDATE/DELETE row is off by the zone
offset (+5 h 30 min there), and the list is ordered by the wrong value.
Explicit rows (auth events, resets) go through Prisma and are right.

**Fix.** Write `now() AT TIME ZONE 'UTC'` (the pattern the TOTP lockout already
uses) in the audit extension. The same raw `now()` also appears in
`auth.service.ts:353`, `portal-auth.service.ts:359` and `:473` (`consumed_at`),
`assignment.service.ts:78` (`clock_timestamp()`), and
`number-sequence.service.ts:34` (`updated_at`, left untouched, see below). None of these is compared to a
UTC value (expiry checks run in app code; `consumed_at` is only tested for null;
round-robin orders by its own column), so the impact is display and ordering,
not access or money.

**Frozen-core note.** `postsales/number-sequence.service.ts` is a Phase 4
financial file. Recommendation: fix the audit extension and the auth/portal/
presales sites in v0.8.3 and **leave `number_sequences.updated_at` alone** (it
is never displayed and never compared) unless the owner approves a one-line
change there.

**Existing rows: decided (2026-10-07).** Existing audit rows are left
unchanged. The release notes explain that rows written before the upgrade may
show times offset by the server's time zone (by 5 h 30 min on a server set to
Asia/Kolkata; not at all on a server in UTC), and that rows written after it are
correct. `number_sequences.updated_at` is left untouched: no frozen-core edit.
Shifting old rows was rejected: the offset is not recorded per row and may not
be constant, so a correction could silently falsify the trail.

**Files:** `packages/db/src/audit.extension.ts`, `auth.service.ts`,

## L. SessionSurfaceGuard: remove the fallback for tokens with no surface claim

**Problem.** Since v0.8.1 access and 2FA-pending tokens carry `surface:
'staff' | 'portal'`. `tokenSurface()` (`apps/api/src/auth/surface.ts`) still
infers the surface from `applicantId`/`brokerId` when the claim is missing, so
that sessions issued before v0.8.1 stayed valid. The transition window (planned
to 2026-10-04) has passed.

**Fix.** A token without a valid `surface` claim is refused (401, so the client
refreshes and gets a claim-bearing token). Keep `tokenIsConsistent` (claim must
agree with the id fields). Remove the inference branch and its comment.

**Effect on users.** Access tokens live 15 minutes and 2FA-pending tokens 5, so
no claim-less token can still be live; any stray one is refused once and the
silent refresh issues a proper one. Effectively invisible, but it is a
behaviour change, so it is in the release notes ("a one-time re-login for any
session that still carries a pre-v0.8.1 token").

**Files:** `apps/api/src/auth/surface.ts`, its guard, `apps/api/test/*surface*`.

**Tests.** Through-the-wire: a hand-signed token with no claim is 401 on a
staff route and on a portal route; a claim-bearing token still works;
inconsistent tokens still 403. Mutation check: restore the inference and the
claim-less test must fail.

**Risk:** low. Size: S.

## Sequencing and release vehicle

**Constraints.** Part S has a fixed release deadline (about 2026-10-28) and is
developed privately. Part B changes CI itself. A private advisory fork runs no
CI. The 71-foreign-key migration (Part A) and the trigger replacement (Part G)
need a rehearsal on a populated database before they ship. Rewriting history
is not acceptable (lesson from the v0.8.2 tag problem); everything must be a
fast-forward.

**Option (i): all of v0.8.3 on the private advisory fork.** Rejected. No CI
means the new CI guards (Part B), the native-install/upgrade jobs and the
Playwright suite would not run on exactly the changes that most need them, and
the large Part A/G work would be tested only by local runs. It also keeps
non-secret work private for no reason.

**Option (ii): public parts on a public branch with CI; Part S developed
privately; joined at release.** Sound mechanism. The join, without revealing
Part S early: the private fork is created from the advisory and is based on
public `master`. Public PRs merge to `master` as they pass CI. Shortly before
release, the private branch is brought up to date with public `master` (fetch
the public repo into the fork, merge or rebase, never rewriting public
history), and the full suite plus a VM rehearsal are run locally (the v0.8.2
method). The advisory's "merge" button then lands Part S on `master`
fast-forward at the moment the advisory is published, and the tag is cut
immediately after. Part S is never visible before that, and the public
repository never contains an unreleased copy of it.

**Option (iii): ship Part S plus the small items as v0.8.3 quickly; the FK and
manifest work becomes v0.8.4.**

**Recommendation: (iii) using (ii)'s mechanism.** Reasons:
1. The deadline belongs to Part S. The foreign-key and trigger work (A, B, G,
   I) is large, touches the frozen financial tables, and needs a populated-DB
   rehearsal; tying Part S to it would put a hard deadline on the riskiest
   migration in the plan.
2. Everything in v0.8.3 is small or medium, application-level, and fully
   testable on public CI (J, K, L, H), so the public branch carries real
   evidence before the private part joins.
3. The integrity work gets its own release, its own rehearsal and its own
   release notes, as the owner's earlier "split the integrity release off"
   decision intended.
4. If H (UA-116) is not ready by 2026-10-21 it simply moves to v0.8.4; nothing
   else depends on it.
